CLI opencodex — це `ocx`. Запустіть `ocx help` (або `--help` / `-h`) для верхньорівневого використання.
Запустіть `ocx help <command>` для команд, зареєстрованих у таблиці довідки. Команди довідки й версії
доступні лише для читання й не запускають, не зупиняють, не встановлюють, не видаляють і не переписують
стан Codex/opencodex.

## Налаштування та життєвий цикл

### `ocx init`

Інтерактивний майстер налаштування. Запитує провайдера (пресет чи власний), API-ключ (літерал чи
`${ENV}`), модель за замовчуванням та порт проксі; зберігає `~/.opencodex/config.json`; опційно інтегрує
проксі в `$CODEX_HOME/config.toml` (за замовчуванням `~/.codex/config.toml`); та опційно встановлює shim
автозапуску Codex.

### `ocx start [--port <port>]`

Запустити сервер проксі (бажаний порт `10100`). Якщо цей порт зайнятий, opencodex вибирає й фіксує інший
доступний порт. Він записує стан PID/runtime-port і відмовляється запускати другий живий екземпляр. Під
час запуску він синхронізує моделі кожного провайдера в каталог Codex. Під час вимкнення він відновлює
нативний Codex — якщо його не було запущено як керовану службу (`OCX_SERVICE=1`).

```bash
ocx start
ocx start --port 8080
```

### `ocx stop`

Зупинити запущений проксі (за PID), вилучити PID-файл і відновити нативний Codex. Якщо встановлено
керовану фонову службу, `ocx stop` також спершу зупиняє її (щоб вона не перезапустила проксі). Та сама
дія доступна з кнопки **Stop** веб-панелі (`POST /api/stop`).

### `ocx restore` &nbsp;·&nbsp; `ocx eject`

Відновити нативний Codex **без** зупинки проксі — прибирає впроваджені рядки конфіга й маршрутизовані
записи каталогу, тож звичайний `codex` знову працює нативно. `eject` — це аліас `restore`.

Передайте `back` до будь-якого написання, щоб знову спрямувати звичайний `codex` на вже запущений
проксі, не змінюючи життєвий цикл проксі:

```bash
ocx restore back
ocx eject back
```

### `ocx recover-history --legacy-openai`

Явне відновлення для старіших збірок розробки, що перемапували історію Codex App до появи підтримки
оборотного резервного копіювання. Спершу закрийте Codex, якщо його база історії заблокована.

### `ocx restart`

Виконати `stop`, за яким іде `ensure`: зупинити проксі/службу, відновити нативний Codex, запустити проксі
у фоні й синхронізувати живий порт назад у Codex.

### `ocx ensure`

Ідемпотентно переконатися, що фоновий проксі працює, потім синхронізувати його живий каталог моделей.
Якщо `codexAutoStart` дорівнює `false`, він друкує, що автозапуск вимкнено, і нічого не робить.

### `ocx status [--json]`

Надрукувати діагностичне зведення лише для читання: PID проксі, досяжність `/healthz`, URL панелі, шлях
конфіга, провайдер за замовчуванням, налаштування автозапуску Codex, стан служби та стан shim.

Використовуйте `--json` для машиночитного контракту діагностики лише для читання:

```bash
ocx status --json
```

Скорочений приклад форми:

```json
{
  "schemaVersion": 1,
  "proxy": {
    "running": false,
    "pid": null,
    "health": {
      "ok": false,
      "url": "http://127.0.0.1:10100/healthz",
      "message": "unreachable"
    }
  },
  "dashboard": {
    "url": "http://localhost:10100/"
  },
  "paths": {
    "config": "/Users/example/.opencodex/config.json",
    "pid": "/Users/example/.opencodex/ocx.pid",
    "runtime": "/path/to/bun"
  },
  "runtime": {
    "source": "bundled"
  },
  "codexAutostart": true,
  "defaultProvider": "openai",
  "service": {
    "summary": "not installed (logs: /Users/example/.opencodex/service.log)"
  },
  "codexShim": {
    "summary": "Codex autostart shim: not installed"
  }
}
```

Справжній об'єкт також включає `listen` (порт, hostname, джерело runtime/config), діагностику
завантаження конфіга та діагностику вбудованого плагіна Codex. JSON-схема лише додавальна: майбутні
версії можуть додати поля, але наявні поля мають залишатися стабільними. Вона навмисно виключає
API-ключі, токени OAuth, заголовки authorization, вміст запитів, e-mail та ідентичності акаунтів.

### `ocx health [--json]`

Перевірити ідентичність живого проксі. Людський вивід повідомляє PID/порт; `--json` видає
`{ok, pid, port}`. Команда завершується з кодом 0 лише коли справна й 1 інакше, що робить її придатною
для проб служби.

### `ocx uninstall` &nbsp;·&nbsp; `ocx remove`

Зупинити службу й проксі, вилучити службу та shim Codex, відновити нативний Codex, потім вилучити
локальний конфіг opencodex лише якщо всі кроки відновлення вдалися. `remove` — це аліас `uninstall`.

## Моделі та Codex

### `ocx sync`

Отримати живий список моделей з кожного налаштованого провайдера й повторно інтегрувати злитий каталог у
Codex. Запускайте його після додавання провайдера чи для оновлення доступних моделей.

### `ocx sync-cache`

Інвалідувати локальний кеш селектора моделей Codex, щоб він перебудувався з активного каталогу
opencodex.

### `ocx v2 [subcommand]`

Керувати прапорцем функції Codex `multi_agent_v2` та 3-становим режимом мультиагентного інтерфейсу.

| Підкоманда | Дія |
| --- | --- |
| `status` (за замовчуванням) | Повідомити поточний прапорець v2, режим мультиагента та конкурентність тредів. |
| `on` | Увімкнути функцію `multi_agent_v2` у `$CODEX_HOME/config.toml` і повторно синхронізувати каталог. |
| `off` | Вимкнути функцію `multi_agent_v2` і повторно синхронізувати. |
| `mode v1` | Примусово перевести ВСІ моделі на v1, вимкнути нативний v2 і зберегти ліміт тредів під `[agents] max_threads`. |
| `mode default` | Поважати вихідні пінування моделей (sol/terra=v2, luna=v1, решта=прапорець codex). Дефолт при встановленні. |
| `mode v2` | Примусово перевести ВСІ моделі на v2, увімкнути нативний v2 і мігрувати той самий ліміт тредів на ключ v2. |
| `threads <n>` | Задати активний ліміт тредів v1/v2 (ціле >= 1). |

```bash
ocx v2 status
ocx v2 mode v1
ocx v2 mode default
ocx v2 on
ocx v2 threads 16
```

Підкоманда `mode` записує `multiAgentMode` у конфіг opencodex і повторно синхронізує каталог Codex.
`mode v1`/`mode v2` та `on`/`off` переміщують поточний числовий ліміт тредів між валідними ключами Codex
v1/v2, перемикаючи нативну функцію через `codex features enable|disable`. Невдалий перехід відновлює
оригінальний `config.toml`. Зміни застосовуються до нових сесій Codex; запущені сесії зберігають свій
запінований інтерфейс.

### `ocx models [--provider <name>] [--json]`

Перелічити моделі, статично додані в налаштованих провайдерах. `--provider` фільтрує одного налаштованого
провайдера, а `--json` повертає метадані моделей плюс нагадування, що `liveModels` може додати записи
лише для runtime. Ця команда не отримує живі каталоги; для цього використовуйте `ocx sync` чи панель.

### `ocx provider <subcommand>`

Неінтерактивне керування провайдерами. Записи реєстру додаються за іменем; власне ім'я потребує і
`--adapter`, і `--base-url`.

| Підкоманда | Підтримувані прапорці | Дія |
| --- | --- | --- |
| `list` | `--json` | Перелічити налаштованих провайдерів та решту записів реєстру. |
| `add <name>` | `--adapter <adapter>`, `--base-url <url>`, `--api-key <key>`, `--default-model <model>`, `--set-default`, `--force`, `--json`, `--sync` | Додати провайдера з реєстру/власного. `--force` перезаписує; `--sync` оновлює запущений проксі в режимі людського виводу. |
| `show <name>` | `--json` | Показати конфіг із маскованими API-ключами. |
| `remove <name>` | `--json` | Вилучити не-типового провайдера; останнього провайдера вилучити не можна. |
| `set-default <name>` | `--json` | Вибрати наявного провайдера як типового. |

```bash
ocx provider list --json
ocx provider add anthropic --api-key sk-ant-... --set-default --sync
ocx provider add local-dev --adapter openai-chat --base-url http://localhost:11434/v1
ocx provider show anthropic --json
ocx models --provider anthropic --json
```

### `ocx account <subcommand>`

Перелічувати й перемикати акаунти провайдерів та пули API-ключів через запущений проксі. Постачений
інтерфейс довідки:

```text
Usage: ocx account <list|current|use|refresh|auto-switch|remove|add-key> ...

List and switch provider accounts and API-key pools (GUI parity).

list [provider]     Codex account pool, OAuth accounts and API keys (identifiers shown masked as the API returns them).
current <provider>  Show the active account or key.
use <provider> <id> Switch the active credential; 'main' selects the Codex App login.
refresh <provider>  Force-refresh Codex or provider quota reports.
auto-switch <provider> <on|off|status|threshold N>  Control the Codex pool threshold.
remove <provider> <id> --yes  Remove a stored account or key after an existence check.
add-key <provider> [--label <label>]  Add a key read only from piped stdin.
Codex pool switches apply to new sessions; running threads keep their account.
```

Усі підкоманди потребують, щоб проксі був запущений; CLI автоматично розв'язує його зафіксований runtime
порт. Успішні операції завершуються з кодом 0. Невалідне використання, невідомий провайдер чи
ідентифікатор акаунта/ключа, недосяжний проксі чи збій API завершуються з кодом 1. Поля облікових даних
відображаються точно так, як їх повертає управлінський API (зокрема його маскування); сирі API-ключі й
токени OAuth ніколи не повертаються. Зручності відображення синтезуються на боці клієнта, як і в панелі:
`main` — це аліас CLI для входу Codex App у пулі акаунтів `openai`, акаунти OAuth без e-mail з'являються
як `Account N`, а стовпець плану/мітки відкочується через план, масковану пошту, мітку та маскований
ключ.

Рядки акаунтів `--json` використовують цю спільну форму (опційні поля опускаються, коли недоступні):

```json
{
  "provider": "openai",
  "type": "codex | oauth | api-key",
  "id": "__main__",
  "label": "plus",
  "email": "m***@example.com",
  "plan": "plus",
  "masked": "sk-ab****wxyz",
  "active": true,
  "needsReauth": false,
  "quota": null
}
```

#### `ocx account list [provider] [--json] [--all]`

Без провайдера перелічує пул Codex, акаунти OAuth та налаштовані пули API-ключів. Порожні провайдери
пропускаються, якщо немає `--all`. З провайдером перелічує лише цю родину облікових даних. Людський вивід
використовує `PROVIDER TYPE ID PLAN/LABEL STATUS`; запінований рядок Codex позначено `next session`. Коли
існує збережений акаунт Kiro, вивід зазначає, що Kiro має один слот входу і що повторний вхід замінює
поточний акаунт. Порожній результат усе одно успіх. `--json` повертає:

```text
{ accounts: AccountRow[], notes: string[] }
```

#### `ocx account current <provider> [--json]`

Показує активний акаунт або ключ. Пул Codex без ручного пінування повідомляє автоматичний вибір із
найменшим використанням; інша родина без активних облікових даних повідомляє цей стан і все одно
завершується з кодом 0. `--json` повертає:

```text
{ provider, type, activeId: string | null, autoSwitchThreshold?: number, account: AccountRow | null }
```

#### `ocx account use <provider> <account-or-key-id|main> [--json]`

Вибирає наявний акаунт Codex, акаунт OAuth чи API-ключ. Для `openai` `main` вибирає вхід Codex App.
Вибори Codex застосовуються лише до **нових сесій**; наявні треди зберігають свій акаунт, а ввімкнений
поріг автоперемикання може пізніше перекрити ручне пінування. Невідомі провайдери чи ідентифікатори
завершуються з кодом 1. `--json` повертає:

```text
{ ok: true, provider, type, activeId }
```

#### `ocx account refresh <provider> [--json]`

Для пулу Codex використовуйте `ocx account refresh openai [--json]`. Він примусово оновлює квоти акаунтів
і друкує доступні тижневі/місячні відсотки та час скидання; відсутні дані квоти повідомляються як
невідомі, а не 0%. Його JSON-конверт — це `{ accounts: AccountRow[] }`, з `quota` на кожному рядку Codex.

Для провайдерів OAuth та API-ключів це примусово оновлює ендпоінт звіту квоти провайдера; це не повторний
вхід токена й не звичайне повторне читання списку акаунтів. `--json` повертає
`{ provider, report: ProviderQuotaReport | null }`. Провайдер без підтримуваного звіту квоти друкує
`no quota report available for <provider>` і завершується з кодом 0. Невідомі провайдери та збої
управлінського API завершуються з кодом 1; проба квоти вихідного провайдера, що зазнає невдачі чи
перевищує таймаут, натомість деградує до null чи застарілого звіту (код 0), відповідаючи смугам квоти
панелі.

#### `ocx account auto-switch <provider> <on|off|status|threshold <0-100>> [--json]`

Керує лише пулом акаунтів Codex `openai`. `on` встановлює 80%, `off` встановлює 0%, `status` читає
поточне значення, а `threshold <n>` приймає ціле від 0 до 100. Інші провайдери та невалідні значення
завершуються з кодом 1. `--json` повертає:

```text
{ provider, autoSwitchThreshold: number, enabled: boolean }
```

#### `ocx account remove <provider> <id|main> --yes [--json]`

Це захищене неінтерактивне видалення потребує `--yes`. Перед видаленням воно перевіряє, що ідентифікатор
існує; відсутній ідентифікатор завершується з кодом 1 без надсилання DELETE. Основний вхід Codex App
видалити не можна, тож `remove openai main --yes` відхиляється. Після видалення родина читається знову:
видалення запінованого акаунта Codex очищає пінування й повертається до автоматичного вибору; OAuth
просуває перший решта акаунт або повідомляє, що жодного немає; пули API-ключів просувають перший решта
ключ або повідомляють, що жодного немає. Форми успіху й невдачі `--json`:

```text
{ ok: true, provider, id, removedActive: boolean, promotedActiveId: string | null }
{ error: string } // stderr, код виходу 1
```

#### `ocx account add-key <provider> [--label <label>] [--json]`

Додає й активує ключ для провайдера з API-ключем. Ключ читається лише з не-TTY переданого/перенаправленого
stdin; інтерактивний TTY-ввід, порожній ввід, провайдери OAuth/Codex та збої API завершуються з кодом 1.
Ключ ніколи не відлунюється, зокрема коли він з'являється всередині мітки. Віддавайте перевагу менеджеру
секретів чи here-string:

```bash
ocx account add-key openrouter --label personal <<< "$OPENROUTER_API_KEY"
security find-generic-password -w openrouter | ocx account add-key openrouter --json
```

`--json` повертає `{ ok: true, id: string | null, label?: string }` і ніколи не включає ключ.

## Автентифікація

### `ocx login <provider>`

Запустити зареєстрований потік входу провайдера. Провайдери OAuth відкривають браузер і зберігають
автооновлювані облікові дані під `~/.opencodex/`; провайдери входу за API-ключем відкривають свою панель
ключів, запитують ключ, валідують його за можливості й зберігають отриманий конфіг провайдера. Команда
друкує наразі прийняті ідентифікатори провайдерів OAuth та API-ключів, коли ім'я відсутнє чи невідоме.

```bash
ocx login xai
```

### `ocx logout <provider>`

Вилучити збережені облікові дані OAuth для провайдера.

## Панель

### `ocx gui`

Відкрити [веб-панель](/opencodex/uk/guides/web-dashboard/) за `http://localhost:<port>`, автоматично
запускаючи проксі, якщо він не працює.

## Фонова служба

### `ocx service [subcommand]`

Запустити opencodex як керовану входом фонову службу (macOS **launchd**, Linux **systemd user unit**,
Windows **Task Scheduler**), що автозапускається при вході й автоперезапускається після збою. Запуски
служби встановлюють `OCX_SERVICE=1`, тож перезапуск не тіпає конфіг Codex.

| Підкоманда | Дія |
| --- | --- |
| немає | Створити/оновити й запустити службу. |
| `install` | Створити й запустити службу. |
| `start` | Запустити встановлену службу. |
| `stop` | Зупинити службу й відновити нативний Codex. |
| `status` | Повідомити, чи працює служба. |
| `uninstall` | Вилучити службу й відновити нативний Codex. |
| `remove` | Аліас `uninstall`. |

```bash
ocx service
ocx service install
ocx service status
ocx service uninstall
```

### `ocx codex-shim <subcommand>`

Обгорнути скриптовий лаунчер `codex` на PATH легким скриптом автозапуску. Справжні цілі `codex.exe`
залишаються недоторканими, щоб не зламати виклики точних виконуваних файлів.

Якщо Codex оновлюється й перезаписує обгортку, shim самовідновлюється при наступному виклику `install` —
новий бінарник резервується й записується свіжа обгортка.

| Підкоманда | Дія |
| --- | --- |
| `install` | Встановити shim (або відремонтувати, якщо застарілий). |
| `uninstall` | Вилучити shim і відновити оригінальний бінарник Codex. |
| `remove` | Аліас `uninstall`. |
| `status` | Повідомити стан shim (встановлено / застарілий / відсутній). |

```bash
ocx codex-shim install
ocx codex-shim status
ocx codex-shim uninstall
```

:::tip[Служба проти Shim]
Використовуйте `ocx service` для завжди ввімкненого фонового проксі (рекомендовано). Використовуйте
`ocx codex-shim` для легкого запуску за потреби без демона — проксі стартує лише коли запускається
`codex`.
:::

## Діагностика

### `ocx doctor`

Запустити діагностику середовища й підключення лише для читання: шляхи стану й тип файлової системи,
подвійні встановлення WSL, середовище/конфіг проксі, досяжність ChatGPT, попередження про плагін Codex та
конфіг проєкту й очікувану міграцію історії. Він друкує підказки з ремонту, але не застосовує їх.

### `ocx debug [provider|usage …]`

Прочитати чи змінити runtime debug-перевизначення через управлінський API запущеного проксі.

```bash
ocx debug provider on|off|status|reset
ocx debug provider logs [-f|--follow]
ocx debug usage on|off|status|reset
ocx debug usage logs [-f|--follow]
```

Без області `ocx debug` друкує використання і, коли проксі зупинено, дефолти середовища наступного
запуску. Debug провайдера дефолтиться з `OCX_DEBUG=1` (застаріле `OCX_DEBUG_FRAMES=1` теж працює); debug
використання дефолтиться з `OPENCODEX_USAGE_DEBUG=1`.

## Оновлення

### `ocx update`

Самооновлення opencodex з npm. Стабільні встановлення використовують `@latest`; preview-встановлення
залишаються на `@preview`, якщо ви не передасте `--tag latest|preview`. Він виявляє checkout вихідного
коду й каже вам натомість зробити `git pull && bun install`, і є no-op, якщо ви вже на найновішій версії
для цього тегу. Запущений проксі зупиняється перед заміною файлів; встановлена служба перебудовується й
запускається автоматично, тоді як встановлення на передньому плані друкує `ocx start` як наступний крок.

```bash
ocx update
ocx update --tag preview
```

Нові версії стають доступними в мить, коли [робочий процес релізу](https://github.com/lidge-jun/opencodex/actions/workflows/release.yml)
публікує їх у npm.

## Довідка

`ocx help`, `ocx --help`, `ocx -h` — друкують верхньорівневе використання й приклади.

`ocx help <command>`, `ocx <command> --help`, `ocx <command> -h` — друкують специфічне для команди
використання для команд, зареєстрованих у `src/cli/help.ts`. Повні контракти підкоманд `provider`,
`debug` та `v2` задокументовано вище.

Невідомі команди залишаються помилками навіть за наявності прапорця довідки, тож скрипти можуть
покладатися на код виходу замість скрапингу тексту.

## Версія

`ocx --version`, `ocx -v`, `ocx version` — друкують один скриптозручний рядок версії й виходять.

## Внутрішні команди

Дві цілі диспетчеризації навмисно опущено зі звичайної довідки: `__refresh-version [preview]` оновлює
кеш сповіщень про оновлення у відокремленому процесі, а `__gui-update-worker <job-id> [latest|preview]
[restart]` запускає завдання оновлення панелі. Це деталі реалізації, а не стабільні команди для
користувача.
