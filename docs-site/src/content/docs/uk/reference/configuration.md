opencodex налаштовується файлом `~/.opencodex/config.json`. Він записується `ocx init` та панеллю, але
ви можете редагувати його безпосередньо; проксі перезавантажує його під час запуску. Якщо файл не
вдається розпарсити (наприклад, обрізаний чи невалідний JSON), opencodex створює резервну копію
`config.json.invalid-<timestamp>`, друкує попередження в консоль і стартує з дефолтами. Відсутні файли
також відкочуються до дефолта (один forward-провайдер `openai`).

## Зарезервовані провайдери OpenAI

`openai` та `openai-apikey` — це фіксовані зарезервовані ідентифікатори. `openai.codexAccountMode` за
замовчуванням `"pool"` і вибирає серед основного плюс доданих акаунтів; `"direct"` використовує лише
поточний вхід викликача/основний. API використовує лише свій налаштований API-ключ/пул ключів.
Використовуйте звичайну модель або `openai-apikey/<model>`; міжмаршрутного відкату облікових даних
немає. Рядки API GPT-5.6 несуть метадані контексту 1 050 000 / макс. вводу 922 000, а Pro-віртуальні
ідентифікатори переписуються в базову мережеву модель з `reasoning.mode: "pro"`.

`openaiProviderTierVersion: 2` позначає поточну одно-провайдерну проєкцію. Перед міграцією постаченого
конфіга v1 opencodex створює `config.json.pre-openai-tiers-v2.bak`, не замінюючи відмінну резервну
копію, і переписує відомі застарілі ідентифікатори з простором імен на звичайні.

| `port` | `number` | `10100` | Порт, який слухає проксі. |
| `hostname?` | `string` | `"127.0.0.1"` | Адреса прив'язки. Встановіть `"0.0.0.0"`, щоб виставити в LAN (потребує `OPENCODEX_API_AUTH_TOKEN`; див. [Віддалений доступ](#remote-access) нижче). |

| `openaiProviderTierVersion?` | `2` | задано міграцією | Позначає одну OpenAI-проєкцію з підтримкою опцій як завершену. |

| `subagentModels?` | `string[]` | `gpt-5.5`, трійка GPT-5.6, `gpt-5.4-mini` | До 5 нативних slug-ів чи ідентифікаторів `provider/model`, виведених першими в селекторі субагентів Codex. Явний порожній список зберігається. |
| `injectionModel?` | `string` | — | Бажана нативна чи маршрутизована модель, названа у впровадженій мультиагентній настанові (інтерфейс v2); делегуванню вказується передати цю точну модель у `spawn_agent` з `fork_turns: "none"`. |
| `injectionEffort?` | `string` | — | Бажане зусилля міркувань `spawn_agent` (`low` до `ultra`). Має сенс лише з `injectionModel`. |
| `effortCap?` | `string` | — | Жорстка стеля зусилля міркувань на запит. Функція мультиагента V2: вона застосовується до основних ходів, чий власний список інструментів несе інтерфейс співпраці V2, плюс до породжених дочірніх ходів, позначених рівно `x-openai-subagent: collab_spawn` чи `"subagent_kind": "thread_spawn"` у `x-codex-turn-metadata` (позначені діти кваліфікуються незалежно від власного інтерфейсу інструментів). Звичайні й V1-інтерфейсні основні ходи не зачіпаються, ходи компакції завжди обходять стелі, а `multiAgentMode: "v1"` цілком вимикає стелі (панель ховає цей блок). Приймає `low` до `ultra`; стелі лише знижують, ніколи не піднімають. Прищипує вниз до найвищої підтримуваної сходинки на рівні стелі чи нижче. Селектор панелі пропонує `low` до `xhigh`. Керується через `GET /api/effort-caps` та `PUT /api/effort-caps`. |
| `subagentEffortCap?` | `string` | — | Та сама жорстка стеля, застосована лише до породжених дочірніх ходів, ідентифікованих маркерами codex-rs, зіставленими точно: `x-openai-subagent: collab_spawn` чи `"subagent_kind": "thread_spawn"` у `x-codex-turn-metadata`. Інші внутрішні категорії субагентів (review, компакція, консолідація пам'яті) ніколи не спрацьовують на цю стелю, а `multiAgentMode: "v1"` цілком її вимикає. Приймає `low` до `ultra`; коли задано обидві стелі, перемагає нижча, і стелі лише знижують, ніколи не піднімають. Прищипує вниз до найвищої підтримуваної сходинки на рівні стелі чи нижче. Якщо модель не має елемента керування зусиллям або жодна підтримувана сходинка не вміщується під стелю, поле зусилля вилучається й застосовується дефолт провайдера. `max` та `ultra` приймаються, але не накладають нижчу стелю рангу (запити прибувають як `low` до `max` після клієнтського перетворення `ultra` → `max`), хоча відомі драбини моделей усе одно можуть спричинити прищипування чи видалення. Селектор панелі пропонує `low` до `xhigh`. Керується через `GET /api/effort-caps` та `PUT /api/effort-caps`. |
| `injectionPrompt?` | `string` | — | Власне перевизначення тіла впровадженої настанови v2. Замінює вбудований текст; плейсхолдери `{{model}}`, `{{effort}}` та `{{roster}}` підставляються. Умови спрацювання незмінні. Задається через `PUT /api/injection-model` (ключ `prompt`). |
| `multiAgentGuidanceEnabled?` | `boolean` | `true` | Керує лише мультиагентною настановою розробника, створеною OpenCodex. Не задано/`true` зберігає настанову v1/v2; `false` придушує обидві, не змінюючи інтерфейс співпраці, `subagentModels`, маршрутизацію чи стелі зусиль. `GET/PUT /api/injection-model` показує ефективне значення; PUT — це часткове оновлення. |
| `disabledModels?` | `string[]` | — | Моделі, приховані від Codex. Маршрутизовані ідентифікатори `provider/model` виключаються з каталогу та `/v1/models`; звичайні нативні GPT-slug-и (наприклад, `gpt-5.4`) перемикають свій запис каталогу на `visibility: "hide"` і випадають зі звичайного списку `/v1/models`. Перемикається на кожну модель зі сторінки Models панелі. |
| `multiAgentMode?` | `"v1" \| "default" \| "v2"` | `"default"` | 3-станове перевизначення мультиагентного інтерфейсу. `"v1"` примусово переводить усі моделі на інтерфейс v1 (перекриває вихідні пінування); `"default"` поважає вихідні пінування (sol/terra=v2, luna=v1); `"v2"` примусово переводить усі моделі на v2. Задається зі сторінки Models панелі чи `ocx v2 mode`. |
| `providerContextCaps?` | `Record<string,number>` | `{}` | Видимі в Codex обмеження контексту для кожного провайдера. Обмеження лише знижує відомі вікна контексту. |
| `contextCapValue?` | `number` | `350000` | Значення, використовуване елементами керування обмеженням контексту в панелі; його зміна оновлює кожен увімкнений запис у `providerContextCaps`. |
| `stallTimeoutSec?` | `number` | `300` | Секунди без вихідних даних, перш ніж міст перерветься й видасть `response.incomplete`. Мінімум 1. |
| `connectTimeoutMs?` | `number` | `200000` | Дедлайн на спробу лише для DNS/TCP/TLS та остаточних заголовків відповіді; він завершується до генерації тіла відповіді. |
| `shutdownTimeoutMs?` | `number` | `5000` | Дедлайн плавного зливання, перш ніж активні ходи буде перервано. |
| `websockets?` | `boolean` | `false` | Оголошувати `supports_websockets`, щоб Codex використовував шлях Responses WebSocket. Опустіть чи встановіть `false`, щоб зберегти HTTP/SSE. |

| `codexAccounts?` | `CodexAccount[]` | `[]` | Метадані пулових акаунтів ChatGPT/Codex, керовані панеллю Codex Auth. Секрети живуть окремо в `codex-accounts.json`. |
| `activeCodexAccountId?` | `string` | — | Пуловий акаунт, використовуваний для наступного нового треда Codex. Наявні афінності тредів зберігають свій оригінальний акаунт. |

| `cacheRetention?` | `"none" \| "short" \| "long"` | `"short"` | Політика кешу промптів Anthropic: вимкнено, 5-хвилинний ефемерний чи 1-годинний розширений. |
| `webSearchSidecar?` | `OcxWebSearchSidecarConfig` | увімкнено | Опції sidecar-а вебпошуку (див. нижче). |
| `visionSidecar?` | `OcxVisionSidecarConfig` | увімкнено | Опції sidecar-а зору (див. нижче). |
| `tokenGuardian?` | `OcxTokenGuardianConfig` | вимкнено | Опційна політика проактивного оновлення OAuth та розігріву акаунтів Codex; поля перелічено нижче. |
| `corsAllowOrigins?` | `string[]` | `[]` | Додаткові точні джерела, дозволені CORS. Loopback-джерела завжди дозволені. |

`maxConcurrentThreadsPerSession` — це поле camelCase, використовуване `PUT /api/v2`, а не ключ
`config.json`. `ocx v2 threads <n>` зберігає відповідне значення `max_concurrent_threads_per_session`
під `[features.multi_agent_v2]` у `$CODEX_HOME/config.toml`; спершу ввімкніть v2, щоб ця таблиця
існувала.

Якщо старіша збірка розробки вже запускала `syncResumeHistory` до появи підтримки резервного
копіювання, ви також можете примусово виконати те саме відновлення нативного провайдера через
`ocx recover-history --legacy-openai`.

:::note[Пул акаунтів Codex]
Використовуйте сторінку **Codex Auth** панелі, щоб додати пулові акаунти й оновити квоти. Конфіг
зберігає лише несекретні метадані акаунтів; токени доступу й оновлення тримаються в захищеному сховищі
облікових даних акаунтів Codex. Наявні ідентифікатори тредів зберігають афінність акаунта, тоді як нові
сесії можуть автомаршрутизуватися на основі квоти, кулдауну й справності.
:::

### claudeCode (OcxClaudeCodeConfig)

Вхідні налаштування Claude Code, споживані інтерфейсом `/v1/messages`, лаунчером `ocx claude` та
сторінкою Claude в GUI. Межі тіла нативної наскрізної передачі (додані з guard-ом зайнятості тіла):

| Ключ | Тип | За замовчуванням | Опис |
| --- | --- | --- | --- |
| `claudeCode.bodyStallSec?` | `number` | `90` | Бюджет неактивності тіла нативної наскрізної передачі в секундах — тиша сирих вихідних байтів, поки читання очікується, ніколи не загальна тривалість. Мін. 1. Рівно `0` вимикає. |
| `claudeCode.bodyMaxBytes?` | `number` | `67108864` | Кумулятивна стеля байтів тіла нативної наскрізної передачі (потоковий SSE та буферизований непотоковий). Рівно `0` вимикає. |

### Форми керованих записів

Записи `apiKeys[]` містять `id: string`, `name: string`, згенерований `key: string` та ISO
`createdAt: string`. Записи `codexAccounts[]` містять обов'язкові поля `id`, `email` та `isMain`, плюс
опційні рядки `plan`, `chatgptAccountId` та безпечний для приватності `logLabel`. Ці записи зазвичай
керуються панеллю.

## Віддалений доступ

За замовчуванням opencodex прив'язується до `127.0.0.1` (лише loopback). Коли `hostname` встановлено на
не-loopback адресу, як-от `0.0.0.0`, opencodex примушує автентифікацію токеном і на управлінському API
(`/api/*`), і на площині даних (`/v1/responses`).

Встановіть змінну середовища `OPENCODEX_API_AUTH_TOKEN` перед запуском:

```bash
export OPENCODEX_API_AUTH_TOKEN="your-secret-token"
ocx start
```

Проксі відмовляється стартувати без цієї змінної під час прив'язки поза loopback. Якщо ви встановлюєте
фонову службу для доступу в LAN, експортуйте цю саму змінну перед `ocx service install`, щоб launchd,
systemd чи Task Scheduler її отримали. Клієнти мають включати токен у кожен запит через заголовок
`x-opencodex-api-key`:

```
x-opencodex-api-key: your-secret-token
```

Заголовок `Authorization: Bearer …` також приймається. Згенеровані панеллю `apiKeys` можна
використовувати замість токена середовища після запуску; усі кандидати порівнюються за сталий час
(`timingSafeEqual`), щоб запобігти часовим бічним каналам.

:::caution[Виставлення в LAN]
Прив'язка до `0.0.0.0` виставляє ваш проксі — та всі налаштовані облікові дані провайдерів — у локальну
мережу. Робіть це лише в довірених мережах і завжди встановлюйте сильний `OPENCODEX_API_AUTH_TOKEN`.
:::

## Провайдери (`OcxProviderConfig`)

| Поле | Тип | Значення |
| --- | --- | --- |

| `baseUrl` | `string` | Base URL вихідного API. |

## Провайдер Cursor (`adapter: "cursor"`)

Міст Cursor експериментальний. Після `ocx login cursor` додайте чи відредагуйте запис `cursor` під
`providers` у `~/.opencodex/config.json` (Windows: `%USERPROFILE%\.opencodex\config.json`).

Повна драбина оптимізації Cursor Router показується як окремі ідентифікатори моделей Codex, бо селектор
моделей Codex не може відрендерити специфічні для Cursor параметри моделі:

| Модель Codex | Режим Cursor Router |
| --- | --- |
| `cursor/auto` | Дефолт команди/акаунта (зворотно сумісний) |
| `cursor/auto-cost` | Cost |
| `cursor/auto-balance` | Balance |
| `cursor/auto-intelligence` | Intelligence |

Явні варіанти всі надсилають модель Cursor `default` з її параметром моделі `optimization`, тож вибір
зберігається на кожен запит. Вони залишаються доступними, коли живе виявлення моделей опускає `default`,
так само як оригінальний запис `cursor/auto`.

За замовчуванням керовані сервером нативні локальні інструменти Cursor залишаються **вимкненими**. Codex
продовжує використовувати власні інструменти (`apply_patch`, `exec_command` тощо) з політикою затвердження
й пісочниці. Використовуйте поле `nativeLocalExec`, щоб вибрати політику:

- **`"off"` (за замовчуванням, найбезпечніше)** — відхиляє все кероване сервером Cursor локальне
  виконання `read`, `write`, `delete`, `ls`, `grep`, `shell` та `fetch`. Використовуйте це, доки ви
  свідомо не підключилися.
- **`"on"` (trusted-local opt-in)** — завжди дозволяє Cursor-нативне локальне виконання для цього
  провайдера. Використовуйте його лише для довіреного локального експерименту на хості, де кожен
  викликач площини даних є довіреним.
- **`"codex-sandbox"` (приймається, падає закрито)** — розпізнається задля зворотної сумісності, але
  наразі поводиться як `"off"`. Текст Responses `instructions` / `system` / `developer` — це керована
  викликачем проза, і opencodex не має надійного підтвердження на кожен запит, що вона відображає
  справжній стан пісочниці Codex, тож воно ніколи не авторизує нативний локальний exec.

```json
{
  "providers": {
    "cursor": {
      "adapter": "cursor",
      "baseUrl": "https://api2.cursor.sh",
      "authMode": "oauth",
      "defaultModel": "auto",
      "nativeLocalExec": "off"
    }
  }
}
```

Поле належить **об'єкту провайдера** (`providers.cursor`), а не верхньому рівню `config.json`.

Ви також можете задати його з [веб-панелі](/opencodex/uk/guides/web-dashboard/): **Providers →
Cursor → Edit JSON**, встановіть `"nativeLocalExec"` у `"off"`, `"on"` чи `"codex-sandbox"`, збережіть,
потім перезапустіть проксі (`ocx restart` або `ocx stop` + `ocx start`).

Застарілий boolean `unsafeAllowNativeLocalExec: true` усе ще приймається й еквівалентний
`nativeLocalExec: "on"`, коли `nativeLocalExec` не задано; явне значення `nativeLocalExec` завжди
перемагає. Віддавайте перевагу `nativeLocalExec` для нових конфігів.

MCP, запис екрана та computer-use використовують окремий конфіг `mcpServers` / `desktopExecutor` і не
керуються цим полем.

### Записи інтеграції Cursor

Кожне значення `mcpServers.<name>` приймає або `command` (stdio), або `url` (Streamable HTTP).
Stdio-записи також приймають `args?: string[]`, `env?: Record<string,string>` та `cwd?: string`;
HTTP-записи приймають `headers?: Record<string,string>`. Обидві форми підтримують `enabled?: boolean`
(за замовчуванням true) та `toolPrefix?: string`.

`desktopExecutor` приймає `computerUseCommand?`, `recordScreenCommand?`, `cwd?`,
`env?: Record<string,string>` та `timeoutMs?` (за замовчуванням `30000`). Команди виконуються через
`sh -c`, читають один JSON-запит зі stdin і мають записати один JSON-результат у stdout.

:::caution[Безпека]
`"off"` — це найбезпечніший дефолт. Типова loopback-прив'язка допускає **будь-який** локальний процес
без автентифікації (зокрема інших локальних користувачів на багатокористувацьких машинах), а текст
запиту, як-от маркери пісочниці Codex, ніколи не авторизує нативний локальний exec. Залиште
`nativeLocalExec` незаданим або встановіть його в `"off"`, доки ви явно не захочете Cursor-нативного
локального виконання, що обходить семантику затвердження й пісочниці Codex.
:::

## Маршрутизація провайдерів OpenRouter

OpenRouter може обслуговувати одну модель через кількох провайдерів висновку. Використовуйте
`openRouterRouting`, щоб тримати запити на бажаних провайдерах, або `modelOpenRouterRouting`, коли різним
моделям потрібні різні ендпоінти. Це особливо корисно для афінності кешу промптів: підтримка кешу,
частота влучань, утримання й ціни можуть суттєво відрізнятися між провайдерами, а автоматичні зміни
провайдера можуть перетворити очікувані влучання в кеш на некешовані запити за повною ціною.

Конфігурація віддзеркалює поля вибору провайдера OpenRouter. Імена провайдерів — це slug-и провайдерів
OpenRouter. `allowFallbacks: false` змушує преференцію падати закрито; `true` дозволяє OpenRouter
використовувати інших прийнятних провайдерів після впорядкованого списку. Список `only` завжди є
allowlist-ом.

```json
{
  "providers": {
    "openrouter": {
      "adapter": "openai-chat",
      "baseUrl": "https://openrouter.ai/api/v1",
      "apiKey": "${OPENROUTER_API_KEY}",
      "openRouterRouting": {
        "order": ["deepseek"],
        "allowFallbacks": false
      },
      "modelOpenRouterRouting": {
        "anthropic/claude-sonnet-5": {
          "only": ["anthropic"],
          "allowFallbacks": false
        }
      }
    }
  }
}
```

Ключі моделей — це точні ідентифікатори моделей OpenRouter, без зовнішнього префікса провайдера
OpenCodex. З наведеним вище прикладом виберіть `openrouter/anthropic-claude-sonnet-5` у Codex; OpenCodex
відновлює нативний ідентифікатор `anthropic/claude-sonnet-5` перед застосуванням модельно-специфічного
правила.

## Статичні allowlist-и моделей

Деякі провайдери надають дуже великі чи повільні живі каталоги моделей. Встановіть `liveModels` у
`false`, коли хочете, щоб Codex бачив лише моделі, запіновані в `models`:

Коли `liveModels` дорівнює `false`, а `models` порожній чи опущений, opencodex не показує маршрутизованих
моделей для цього провайдера.

Використовуйте `selectedModels` для іншої мети: виявлення все одно виконується, але лише вибрані
ідентифікатори публікуються в каталог Codex та `/v1/models`. Повний список моделей панелі залишається
доступним, тож allowlist можна змінити пізніше.

Прев'ю-резервні записи GPT-5.6 використовують той самий механізм. Пресет OpenAI API-ключа засіває базові
й Pro-ідентифікатори з контекстом `1050000` та макс. вводом `922000`; пресет OpenRouter засіває
`openai/gpt-5.6-sol`, `openai/gpt-5.6-terra` та `openai/gpt-5.6-luna` з контекстом `1050000`. Контракт
каталогу Codex для Pool/Direct — це `372000`, а синхронізований каталог Codex оголошує міркування `max`,
тримаючи `xhigh` окремим. Залиште `liveModels` увімкненим, щоб злити живі результати провайдера з цими
явними доповненнями, або встановіть його в `false`, щоб показати лише `models`.

```json
{
  "providers": {
    "openrouter": {
      "adapter": "openai-chat",
      "baseUrl": "https://openrouter.ai/api/v1",
      "apiKey": "${OPENROUTER_API_KEY}",
      "liveModels": false,
      "models": ["deepseek/deepseek-v4-flash", "qwen/qwen3-coder-plus"]
    }
  }
}
```

| `backend?` | `"openai" \| "anthropic"` | авто | Бекенд executor-а. Явний конфіг перемагає; коли опущено, придатний збережений акаунт Anthropic OAuth вибирає `anthropic`, інакше `openai`. |
| `model?` | `string` | залежить від бекенда | Модель пошуку: `gpt-5.6-luna` для `openai`, `claude-sonnet-5` для `anthropic`. Явні застарілі значення `gpt-5.4-mini` мігрують під час запуску. |
| `reasoning?` | `string` | `low` | Зусилля міркувань для sidecar-а (`minimal` відхиляється з вебпошуком). |
| `maxSearchesPerTurn?` | `number` | `3` | Загальна кількість справжніх пошуків на хід основної моделі (guard циклу). |
| `routedModelStallTimeoutMs?` | `number` | `200000` | Лише-конфіговий дедлайн безперервної неактивності сирих байтів відповіді для кожної ітерації маршрутизованої моделі. Має бути цілим від `1` до `2147483647`; кожен непорожній чанк тіла відповіді його скидає. |
| `timeoutMs?` | `number` | `200000` | Окремий дедлайн для одного хостованого запиту вебпошуку. |

Бекенд `openai` запускає хостований пошук через увімкнений провайдер ChatGPT `forward`, тож йому
потрібен і вхід у ChatGPT, і цей провайдер. На маршрутизованих повторах із вхідним Claude opencodex
впроваджує основну автентифікацію ChatGPT у внутрішній запит sidecar-а, тож цей шлях залишається
досяжним. Бекенд `anthropic` використовує активні збережені облікові дані з увімкненого провайдера
Anthropic OAuth і запускає інструмент Claude `web_search_20250305`. Якщо `backend: "anthropic"` явний,
але жоден активний акаунт не придатний (зокрема `needsReauth`), sidecar падає закрито замість відкату до
OpenAI.

Шлях вебпошуку має чотири годинники: базовий бюджет застою подій мосту (`stallTimeoutSec`), бюджет
DNS/TCP/TLS/остаточного заголовка (`connectTimeoutMs`), неактивність сирих байтів маршрутизованої моделі
(`routedModelStallTimeoutMs`) та один хостований пошук (`timeoutMs`). Його ефективний watchdog мосту —
`max(базовий застій, таймаут з'єднання, застій маршрутизованої моделі, таймаут sidecar-а) + 30 секунд`.
Застій маршрутизованої моделі — це guard неактивності, а не загальний таймаут генерації.

### `visionSidecar` (`OcxVisionSidecarConfig`)

| Поле | Тип | За замовчуванням | Значення |
| --- | --- | --- | --- |
| `enabled?` | `boolean` | увімкнено, коли вибраний бекенд придатний | Головний перемикач. Встановіть `false`, щоб вимкнути описи зображень. |
| `backend?` | `"openai" \| "anthropic"` | авто | Бекенд executor-а. Використовує те саме розв'язання з пріоритетом явного й урахуванням облікових даних Anthropic, що й вебпошук. |
| `model?` | `string` | залежить від бекенда | Модель опису зображень: `gpt-5.4-mini` для `openai`, `claude-sonnet-5` для `anthropic`. |
| `maxDescriptionsPerTurn?` | `number` | `8` | Максимум нових промахів кешу опису, допущених в одному ході основної моделі. `0` вимикає виклики опису; невалідні значення використовують дефолт. |
| `timeoutMs?` | `number` | `45000` | Таймаут fetch sidecar-а. |

Зір активується лише для зображень, надісланих моделі, яку зіставлено списком `noVisionModels` її
провайдера. Бекенд OpenAI має ті самі вимоги входу + forward-провайдера, що й вебпошук; бекенд Anthropic
використовує збережений OAuth і падає закрито, коли явно вибраний без придатних облікових даних. Успішні
описи `data:`-зображень кешуються в обмеженому кеші на рівні процесу, ключованому за бекендом, моделлю,
деталізацією, байтами зображення й нормалізованим контекстом повідомлення. Влучання в кеш і дублікати в
межах того самого ходу не витрачають `maxDescriptionsPerTurn`. Віддалені `https:`-зображення та
невдалі/порожні описи не кешуються.

Запити пошуку та опису зображень через Anthropic-OAuth повторно використовують наявний OAuth-фінгерпринт
Claude Code в opencodex. Це в межах наявного OAuth-прецеденту репозиторію, але їх варто протестувати під
навантаженням із призначеним акаунтом і робочим навантаженням.

## Повний приклад

```json
{
  "port": 10100,
  "defaultProvider": "openai",
  "providers": {
    "openai": {
      "adapter": "openai-responses",
      "baseUrl": "https://chatgpt.com/backend-api/codex",
      "authMode": "forward"
    },
    "anthropic": {
      "adapter": "anthropic",
      "baseUrl": "https://api.anthropic.com",
      "authMode": "oauth",
      "defaultModel": "claude-sonnet-4-6"
    },
    "ollama-cloud": {
      "adapter": "openai-chat",
      "baseUrl": "https://ollama.com/v1",
      "apiKey": "${OLLAMA_API_KEY}",
      "defaultModel": "glm-5.2",
      "noVisionModels": ["glm-5.2", "gpt-oss", "qwen3-coder", "deepseek-v4-pro"]
    }
  },
  "subagentModels": ["anthropic/claude-opus-5", "ollama-cloud/glm-5.2"],
  "disabledModels": [],
  "websockets": false,
  "webSearchSidecar": {
    "maxSearchesPerTurn": 3,
    "routedModelStallTimeoutMs": 200000,
    "timeoutMs": 200000
  },
  "visionSidecar": { "enabled": true }
}
```

:::tip[Секрети]
Віддавайте перевагу посиланням `${ENV_VAR}` для ключів, щоб `config.json` залишався вільним від
секретів. Провайдери OAuth та forward взагалі не зберігають ключа.
:::

:::note[Атомарні записи]
Усі файли конфіга й каталогу (`config.toml`, `opencodex-catalog.json`) записуються атомарно через
`atomicWriteFile` (тимчасовий файл + перейменування). Це запобігає напівзаписаним файлам, коли конкурентні
записувачі — наприклад, `ocx stop` та власний обробник вимкнення проксі — одночасно відновлюють Codex.
:::
