---

opencodex не патчить Codex App. Він записує ту саму конфігурацію Codex і каталог моделей, які вже
використовують Codex CLI/TUI. Оскільки Codex App читає цей спільний стан, маршрутизовані моделі можуть
з'являтися в селекторі моделей App як звичайні записи каталогу Codex.

Записи OpenAI мають дві стабільні ідентичності: одна звичайна нативна група `openai`, чий вибір акаунта
Pool (за замовчуванням) або Direct керується `codexAccountMode`, і транспорт з API-ключем із простором
імен `openai-apikey/<model>`. Зміна режиму акаунта не змінює ідентифікаторів селектора. API-записи
GPT-5.6 використовують контекст 1 050 000 / макс. ввід 922 000, а ідентифікатори селектора `*-pro`
розв'язуються в базову мережеву модель з `reasoning.mode: "pro"`, тоді як журнали, використання та стан
селектора зберігають віртуальний ідентифікатор. API-каталог зафіксовано рівно на восьми
ідентифікаторах: `gpt-5.5`, `gpt-5.6`, Sol/Terra/Luna та їхні три Pro-віртуальні ідентифікатори;
загального аліаса `gpt-5.6-pro` немає. Compact-запити зберігають вибраний тариф, але надсилають базову
модель без об'єкта міркувань.

Виберіть обліковий маршрут явно; змініть Pool/Direct на сторінці Providers:

```text
gpt-5.6-sol                         # openai (опція Pool або Direct)
openai-apikey/gpt-5.6-sol           # API-ключ
```

Свіжі встановлення та конфіги без збереженого режиму за замовчуванням використовують Pool. Поточні
конфіги використовують маркер 2 і зберігають постачене джерело v1 у
`~/.opencodex/config.json.pre-openai-tiers-v2.bak`; відновіть його командою:

```sh
cp ~/.opencodex/config.json.pre-openai-tiers-v2.bak ~/.opencodex/config.json
```

Ранні конфігурації v1 із трьома провайдерами мігрують автоматично в єдиний рядок з підтримкою опцій.

## Шлях інтеграції

`ocx init`, `ocx start` та `ocx sync` тримають ці файли Codex узгодженими під розв'язаною директорією
`CODEX_HOME`:

```text
$CODEX_HOME/config.toml
$CODEX_HOME/opencodex.config.toml
$CODEX_HOME/opencodex-catalog.json
$CODEX_HOME/models_cache.json
```

На типовій loopback-прив'язці Codex зберігає свій вбудований ідентифікатор провайдера `openai`.
opencodex встановлює кореневі ключі, що вказують провайдера й каталог моделей на проксі:

```toml
model_catalog_json = "/absolute/path/to/opencodex-catalog.json"
openai_base_url = "http://127.0.0.1:10100/v1"
```

Для не-loopback hostname Codex також потрібен згенерований заголовок API-автентифікації. Цей режим
використовує кореневий ключ `model_provider = "opencodex"` та окремого Responses-сумісного провайдера:

```toml
[model_providers.opencodex]
name = "OpenCodex Proxy"
base_url = "http://your-host:10100/v1"
wire_api = "responses"
requires_openai_auth = true
env_http_headers = { "x-opencodex-api-key" = "OPENCODEX_API_AUTH_TOKEN" }
```

`websockets` вимкнено за замовчуванням. Записи окремого провайдера й каталогу оголошують
`supports_websockets = true` лише коли `"websockets": true`; на loopback вбудований провайдер Codex
може спершу зондувати WebSocket, і вимкнений проксі повертає `426`, тож Codex відкочується на HTTP/SSE.
Див. [Інтеграцію з Codex](/opencodex/uk/guides/codex-integration/) щодо повного потоку інтеграції та
відновлення.

## Чому маршрутизовані моделі з'являються

Селектор моделей Codex очікує записи каталогу у формі Codex. opencodex будує маршрутизовані записи,
клонуючи шаблон нативної моделі Codex, а потім замінюючи ідентичність маршрутизованої моделі:

```text
slug = "anthropic/claude-sonnet-..."
display_name = "anthropic/claude-sonnet-..."
visibility = "list"
```

Клон зберігає поля суворого парсера, як-от рівні міркувань, тип shell, прапорці підтримки API та базові
інструкції. opencodex потім вилучає лише-нативні можливості, які маршрут не може виконати, зокрема
метадані сервісного тарифу OpenAI.

## Покриття моделей у v2.7.1

Набір нативного резерву включає `gpt-5.5`, `gpt-5.4`, `gpt-5.4-mini`, `gpt-5.3-codex-spark` та GPT-5.6
Sol/Terra/Luna. Для родини GPT-5.5/5.4 opencodex зберігає багатші живі записи встановленого каталогу
Codex і лише синтезує відсутній запис. Вбудований вихідний знімок використовується лише для GPT-5.6, де
він постачає справжню ідентичність та метадані для кожної моделі замість наближення зі старішого
шаблону.

| Маршрут | Ідентифікатори селектора та метадані каталогу |
| --- | --- |
| Вхід у Codex (Pool або Direct) | `gpt-5.6-sol`, `gpt-5.6-terra`, `gpt-5.6-luna` (вікно каталогу 372 000 токенів) |
| OpenAI (API-ключ) | Рівно вісім рядків із простором імен: `gpt-5.5`, `gpt-5.6`, Sol/Terra/Luna та три `*-pro`-віртуальні ідентифікатори (контекст 1 050 000; макс. ввід 922 000 для всіх восьми) |
| OpenRouter | `openrouter/openai/gpt-5.6-sol`, `openrouter/openai/gpt-5.6-terra`, `openrouter/openai/gpt-5.6-luna` (1 050 000) |
| Cursor | Статичний резерв включає `cursor/gpt-5.6-sol`, `cursor/gpt-5.6-terra` та `cursor/gpt-5.6-luna` (1 000 000), плюс `cursor/grok-4.5` та `cursor/grok-4.5-fast` (500 000); живе виявлення акаунта вирішує, які залишаться видимими. |
| xAI | Живе виявлення авторитетне; резервний каталог за замовчуванням має `xai/grok-4.5` з вікном 500 000 токенів та елементами керування міркуваннями `low` / `medium` / `high`. |

Запіновані записи GPT-5.6 зберігають точну вихідну драбину. Sol і Terra надають `low` до `ultra`; Luna
зупиняється на `max`. Sol за замовчуванням `low`, тоді як Terra й Luna за замовчуванням `medium`.
`ultra` — це вибір з боку клієнта для максимальних міркувань плюс проактивне делегування, і він досягає
бекенда як `max`. Запис у селекторі означає лише те, що каталог готовий: під'єднаний акаунт або
API-ключ усе одно повинен мати право використовувати цю модель.

## Перемикачі нативних і маршрутизованих моделей

Сторінка Models панелі використовує `disabledModels` для обох родин моделей:

- Маршрутизовані ідентифікатори мають простір імен (`provider/model`). Вимкнення одного виключає його зі
  синхронізованого каталогу та `/v1/models`.
- Нативні GPT-ідентифікатори — це звичайні slug-и. Вимкнення одного зберігає його запис каталогу, але
  змінює `visibility` на `hide`, зберігаючи точний запис для пізнішого повторного ввімкнення; звичайна
  форма списку OpenAI опускає його на час вимкнення.
- Нативні рядки походять із підтримуваного статичного набору, тож вимкнена нативна модель залишається
  видимою в панелі й може бути знову ввімкнена.

Прохід видимості виконується після оновлень знімка, а управлінський API оновлює каталог і примусово
робить кеш моделей Codex застарілим після перемикання.

## Режим мультиагентного інтерфейсу

opencodex додає 3-станове перевизначення поля `multi_agent_version` на кожному записі каталогу:

| Режим | Ефект |
| --- | --- |
| **v1** | Примусово перевести кожну модель на мультиагентний інтерфейс v1, перекриваючи вихідні пінування (зокрема Sol/Terra). |
| **base** (за замовчуванням при встановленні) | Відновити вихідні пінування: Sol/Terra використовують v2, Luna використовує v1, а незапіновані моделі йдуть за прапорцем функції Codex `multi_agent_v2`. |
| **v2** | Примусово перевести кожну модель на мультиагентний інтерфейс v2, перекриваючи вихідні пінування (зокрема Luna). |

Встановіть режим із панелі чи сторінки Models, `ocx v2 mode v1|default|v2` або `PUT /api/v2` з
`{ "multiAgentMode": "v1" }`. Зміни застосовуються до нових сесій Codex.

:::caution
На інтерфейсі v2 (`multi_agent_v2`) породжені субагенти успадковують модель батьківської сесії.
Селектор моделі/зусилля делегування в панелі — це настанова промпту v1, а не міжмодельний роутер на
кожне породження на боці проксі. Див. [Інтерфейс субагентів](/opencodex/uk/guides/sub-agent-surface/)
щодо канонічної поведінки.
:::

## Верхні рівні міркувань

Видимість рівнів міркувань не залежить від режиму інтерфейсу v1/base/v2. Згенеровані записи, здатні до
міркувань, оголошують `max`, щоб прямі перевизначення зусилля субагента валідувалися; поточні
згенеровані маршрутизовані записи та старіші нативні GPT-записи також оголошують `ultra`. Точні вихідні
драбини GPT-5.6 збережено, тож Luna має `max`, але не `ultra`.

На дроті маршрутизовані адаптери відображають або обмежують непідтримувані рівні. Для старіших нативних
моделей, чия справжня драбина зупиняється на `xhigh`, `nativeEffortClamp` відображає прямий `max` чи
вибір `ultra` на `xhigh` (наприклад, GPT-5.5). Sol, Terra й Luna мають справжню сходинку `max`.

## Правила швидкого тарифу

Codex зберігає швидкий режим як:

```toml
service_tier = "fast"

[features]
fast_mode = true
```

Але каталог моделей та ідентифікатор тарифу запиту під час виконання використовують `priority`.
opencodex зберігає цей поділ. Нативні наскрізні моделі OpenAI зберігають підтримку fast; маршрутизовані
моделі не від OpenAI прибирають метадані сервісного тарифу, тож опція fast не оголошується там, де її
не можна виконати.

## Вибір субагентів

Codex сортує видимі в селекторі записи каталогу за зростаючим `priority` й оголошує перші п'ять як
перевизначення моделей `spawn_agent`. Виберіть до п'яти звичайних нативних ідентифікаторів або
ідентифікаторів `provider/model` із простором імен через `subagentModels` чи сторінку Subagents панелі;
opencodex дає цим записам пріоритети 0–4 у вибраному порядку. Інші моделі залишаються викликуваними за
точним ідентифікатором.

Список виведених моделей окремий від настанови **Делегування субагентів** у панелі. Зокрема,
перевизначення виведених моделей не обходять правило успадкування батьківської моделі в v2.

## Оновлення стану моделей

Якщо селектор усе ще показує застарілі записи, оновіть каталог і перезапустіть цільовий інтерфейс Codex:

```bash
ocx sync
```

opencodex перезаписує `models_cache.json` навмисно застарілою обгорткою кешу щоразу, коли змінюється
видимість, пріоритет чи метадані каталогу, тож наступне оновлення моделей Codex читає новий каталог.
