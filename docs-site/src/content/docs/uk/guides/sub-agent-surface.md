title: Інтерфейс субагентів (v1 / base / v2)

---

opencodex дає змогу вибрати інтерфейс мультиагентної співпраці для кожної моделі в каталозі. Перемикач **Субагент** у панелі та на сторінці Models керує цим глобально.

:::note
На інтерфейсі v2 (`multi_agent_v2`) породжений субагент **за замовчуванням** успадковує батьківську модель: `fork_turns` за замовчуванням `all`, а форки з повною історією відхиляють перевизначення. Починаючи з v2.7.2, opencodex впроваджує настанову, яка навчає модель, як розірвати успадкування — виклик `spawn_agent`, що встановлює `fork_turns` у `"none"` (або частковий форк, як-от `"3"`), може передати аргументи `model` / `reasoning_effort`, які середовище виконання Codex парсить і застосовує, навіть попри те, що опублікована схема інструмента їх приховує. Відоме обмеження: коли **нативний** батько породжує дитину, маршрутизовану до **ненативного** провайдера, клієнт Codex може надіслати корисне навантаження `NEW_TASK` лише як зашифроване бекендом `encrypted_content`, тож маршрутизована дитина отримує порожнє тіло задачі ([#92](https://github.com/lidge-jun/opencodex/issues/92)). Перевизначення моделі все одно застосовується, але текст задачі може загубитися — інтерфейс v1 залишається надійним вибором для делегування між різними провайдерами.
:::

## Режими

| Режим | Інтерфейс | Поведінка |
| --- | --- | --- |
| **v1** | `multi_agent_v1` | Класичні інструменти агентів із простором імен та `send_input` / `close_agent` / `resume_agent`. Перевизначення моделі в `spawn_agent` може запустити субагента на іншій моделі. |
| **base** (за замовчуванням) | Вихідні пінування | Відновлює вихідні пінування моделей: gpt-5.6-sol і gpt-5.6-terra використовують v2, gpt-5.6-luna використовує v1, а незапіновані моделі йдуть за прапорцем функції Codex `multi_agent_v2`. Поведінка породження йде за інтерфейсом, що розв'язується для цієї моделі. |
| **v2** | `multi_agent_v2` | Пласкі інструменти `spawn_agent` з паралельними сесіями та `send_message` / `followup_task` / `wait_agent` / `interrupt_agent`. Діти успадковують батьківську модель на форках із повною історією; `fork_turns: "none"` (або частковий форк) приймає перевизначення `model` / `reasoning_effort`. Тіло задачі може прибувати зашифрованим для дітей native→routed ([#92](https://github.com/lidge-jun/opencodex/issues/92)). |

## Як це працює

Режим встановлює поле `multi_agent_version` на кожному записі каталогу, який читає Codex:

- **режим v1**: примусово встановлює `multi_agent_version = "v1"` на всіх записах, перекриваючи вихідні пінування.
- **режим base**: відновлює вихідні значення за замовчуванням. Запіновані моделі отримують своє знімкове значення; незапіновані моделі опускають поле, тож рішення приймає прапорець функції Codex.
- **режим v2**: примусово встановлює `multi_agent_version = "v2"` на всіх записах, перекриваючи вихідні пінування.

Перевизначення — це фінальний прохід і в живій відповіді каталогу `/v1/models`, і в синхронізації каталогу на диску. Тому зміни режиму застосовуються послідовно до новостворених сесій, незалежно від того, як було побудовано запис.

### Модель і зусилля делегування

Селектор **Делегування субагентів** у панелі зберігає `injectionModel` та, опційно, `injectionEffort`. Це налаштування настанови з делегування, а не роутер породження на боці проксі. Опційний `injectionPrompt` цілком замінює вбудований текст настанови.

`multiAgentGuidanceText` визначає інтерфейс з інструментів запиту — зокрема шлях WebSocket Codex Desktop (`responses_lite`), де інструменти прибувають усередині вхідного елемента `additional_tools`, а не в масиві `tools` запиту.

На ході **v2** (Sol/Terra у режимі base, кожна модель у режимі v2) проксі впроваджує компактний блок настанови — з бюджетом 700 символів — щоразу, коли задано прийнятну модель впровадження або ефективний ростер субагентів непорожній. Блок умовно описує перевизначення `model` / `reasoning_effort`, не припускаючи, чи з'являються вони в активній схемі, вимагає `fork_turns: "none"` (або частковий форк), називає лише прийнятну канонічну бажану модель і перелічує лише налаштовані моделі з перших п'яти видимих у селекторі Codex, сумісних з v2, відсортованих за пріоритетом, із їхніми доступними драбинами зусиль.

На ході **v1** проксі лише віддзеркалює текст проактивного делегування вихідного провайдера на найвищому рівні зусилля (max / ultra). Жодного призначення моделі, ростера чи власного промпту там не додається — v1 за задумом залишається легким.

Щоб замінити вбудовану настанову v2, встановіть `injectionPrompt` (ключ конфіга або `PUT /api/injection-model` зі значенням `prompt`). Плейсхолдери `{{model}}`, `{{effort}}` та `{{roster}}` підставляються налаштованою моделлю впровадження, зусиллям і розв'язаним рядком ростера. Умови спрацювання незмінні: власний промпт ніколи не змушує хід спрацювати там, де інакше він мовчав би.

## Зміна режиму

### GUI

- **Панель** → перша статистична комірка: клацніть **v1**, **base** чи **v2**.
- Сторінка **Models** → сегментований елемент керування у верхньому рядку.
- Обидві сторінки мають кнопку **?**, що відкриває довідкове модальне вікно з посиланням назад сюди.
- **Панель** → **Делегування субагентів**: виберіть бажану модель і опційне зусилля міркувань. На v2 впроваджена настанова інструктує агента породжувати з `fork_turns: "none"`, щоб перевизначення моделі застосувалося — хоча для дітей native→routed тіло задачі наразі може прибувати зашифрованим ([#92](https://github.com/lidge-jun/opencodex/issues/92)).

### CLI

```bash
ocx v2 mode v1       # примусово перевести всі моделі на v1
ocx v2 mode default  # відновити вихідні пінування
ocx v2 mode v2       # примусово перевести всі моделі на v2
ocx v2 status        # показати поточний режим + прапорець функції Codex
```

### API

```bash
# Прочитати режим інтерфейсу, прапорець функції та ліміт тредів
curl http://localhost:10100/api/v2

# Встановити режим інтерфейсу
curl -X PUT http://localhost:10100/api/v2 \
  -H 'Content-Type: application/json' \
  -d '{"multiAgentMode": "v2"}'
```

Ендпоінт PUT `/api/v2` також приймає `enabled` (boolean, прапорець функції Codex) та `maxConcurrentThreadsPerSession` (ціле). Він валідує запит, зберігає режим, повторно синхронізує каталог і повідомляє, що зміни режиму застосовуються до нових сесій.

Селектор делегування використовує окремий ендпоінт:

```bash
# Прочитати поточну модель/зусилля та доступні значення селектора
curl http://localhost:10100/api/injection-model

# Встановити обидва значення
curl -X PUT http://localhost:10100/api/injection-model \
  -H 'Content-Type: application/json' \
  -d '{"model": "anthropic/claude-sonnet-5", "effort": "xhigh"}'

# Встановити власний промпт настанови (плейсхолдери {{model}}/{{effort}}/{{roster}})
curl -X PUT http://localhost:10100/api/injection-model \
  -H 'Content-Type: application/json' \
  -d '{"model": "anthropic/claude-sonnet-5", "prompt": "Delegate to {{model}}.{{roster}}"}'

# Очистити обидва значення
curl -X PUT http://localhost:10100/api/injection-model \
  -H 'Content-Type: application/json' \
  -d '{"model": null}'
```

`GET /api/injection-model` повертає `model`, `effort`, `prompt`, глобальну драбину `efforts` та ввімкнені нативні/маршрутизовані моделі `available`. Для PUT опускання `effort` чи `prompt` зберігає поточне значення, `null` його очищає, а очищення `model` завжди очищає й зусилля. API валідує зусилля щодо глобальної драбини Codex; Codex усе одно валідує зусилля породження щодо цільового запису каталогу.

## Зусилля міркувань

Опційне налаштування зусилля субагента зберігається як `injectionEffort` і має сенс лише з моделлю впровадження. Воно додає інструкцію `reasoning_effort` до впровадженої настанови v2; воно не змінює зусилля батьківської сесії. На будь-якому форку, що приймає перевизначення, Codex застосовує `reasoning_effort`, переданий у `spawn_agent`, безпосередньо.

`ultra` стоїть вище за `max` у каталозі Codex і додає семантику автоматичного делегування, але воно ніколи не досягає провайдера як буквальне мережеве значення. Codex перетворює `ultra` на `max` на межі клієнта. opencodex далі тримає запит провайдера валідним:

| Модель | `max` на дроті | Вибір `ultra` на дроті |
| --- | --- | --- |
| gpt-5.5, gpt-5.4, gpt-5.4-mini | xhigh | xhigh (через max, потім `nativeEffortClamp`) |
| gpt-5.6-sol, gpt-5.6-terra | max | max |
| gpt-5.6-luna | max | Не оголошується його точною вихідною драбиною |
| Маршрутизовані моделі | Відображено або обмежено адаптером | Перетворено на max, потім відображено або обмежено адаптером |

Доступність у каталозі не залежить від режиму v1/v2. Згенеровані записи, здатні до міркувань, оголошують `max`, щоб прямі перевизначення зусилля субагента валідувалися; поточні згенеровані маршрутизовані записи також оголошують `ultra`. Точні вихідні драбини моделей збережено, тому gpt-5.6-luna зупиняється на `max`.

## Обмеження контексту

Глобальне значення обмеження контексту за замовчуванням дорівнює 350k і обмежує оголошуване `context_window` лише для маршрутизованих провайдерів, чиє обмеження ввімкнено. Нативні моделі OpenAI зберігають свої справжні вікна контексту.

Змініть значення чи налаштування для всіх провайдерів на сторінці Models або перемкніть обмеження поряд із заголовком групи окремого провайдера.
