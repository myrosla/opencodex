opencodex змушує Codex маршрутизуватися через проксі, редагуючи дві речі, які читає Codex: його конфіг
(`$CODEX_HOME/config.toml`, за замовчуванням `~/.codex/config.toml`) та його каталог моделей. Кожне
редагування ідемпотентне й оборотне.

Проксі надає один звичайний маршрут входу в Codex `openai` з режимами акаунтів Pool (за замовчуванням)
і Direct, плюс `openai-apikey/<model>` для налаштованого API-ключа. Pool включає основний плюс додані
акаунти; Direct використовує лише bearer викликача/основного входу. Маршрути не відкочуються один до
одного. Постачені конфіги v1 мігрують до маркера 2 і зберігають `config.json.pre-openai-tiers-v2.bak`
для ручного відновлення.

## Інтеграція конфіга

`ocx init`, `ocx start` та `ocx sync` викликають інтегратор. На типовій loopback-прив'язці він зберігає
вбудований ідентифікатор провайдера `openai` у Codex і вказує цього провайдера на opencodex:

```toml
# кореневі ключі, перед першою таблицею
model_catalog_json = "/absolute/path/to/opencodex-catalog.json"
# Auto-injected by opencodex
openai_base_url = "http://127.0.0.1:10100/v1"

[features]
fast_mode = true
```

Проксі за замовчуванням слухає на порту `10100` й обслуговує `POST /v1/responses`,
`POST /v1/responses/compact`, `POST /v1/images/generations`, `POST /v1/images/edits`,
`GET /v1/models`, `GET /healthz` та управлінський інтерфейс `/api/*`.

### Вбудована генерація зображень (`image_gen`)

Вбудований інструмент Codex `image_gen` не проходить через `/v1/responses` — розширення codex-rs робить
POST безпосередньо на `{base_url}/images/generations` (або `/images/edits`, коли додано референсні
зображення) з тією самою bearer-автентифікацією ChatGPT, яку воно використовує для чату. Оскільки
впроваджений `base_url` вказує на opencodex, проксі ретранслює ці виклики на вихідний OpenAI:

- **Один кандидат перенаправлення з урахуванням режиму:** Pool вибирає прийнятний основний/доданий
  акаунт; Direct використовує OAuth-bearer викликача. Налаштований режим послідовно застосовується до
  запиту зображення.
- **Провайдер OpenAI з API-ключем:** він використовується лише тоді, коли жоден кандидат перенаправлення
  не має збою автентифікації. Зламані/прострочені облікові дані Pool ніколи не приховуються за окремо
  оплачуваним використанням API.
- **Жодного:** проксі повертає зрозумілу помилку замість загального 404. Маршрутизовані провайдери
  (Cursor, Gemini, Kiro, …) не можуть обслуговувати генерацію зображень; якщо ви взагалі не хочете, щоб
  інструмент пропонувався, вимкніть його в Codex через `codex features disable image_generation`
  (`[features] image_generation = false` у `config.toml`).

Для не-loopback `hostname` Codex має надсилати згенерований заголовок API-автентифікації. Тому
інтегратор натомість використовує окремого провайдера:

```toml
# кореневі ключі
model_provider = "opencodex"
model_catalog_json = "/absolute/path/to/opencodex-catalog.json"

# додано в кінці файлу
# Auto-injected by opencodex
[model_providers.opencodex]
name = "OpenCodex Proxy"
base_url = "http://your-host:10100/v1"
wire_api = "responses"
requires_openai_auth = true
env_http_headers = { "x-opencodex-api-key" = "OPENCODEX_API_AUTH_TOKEN" }
# supports_websockets = true   # лише коли config.websockets дорівнює true
```

Коли OpenCodex володіє маршрутизацією, обидва режими записують `$CODEX_HOME/opencodex.config.toml` як
еталонний/резервний конфіг. На loopback він містить кореневі ключі, які ви можете злити вручну, якщо
автоматичну інтеграцію було вилучено; на не-loopback він містить форму окремого провайдера. Режим
зовнішнього провайдера залишає цей профіль недоторканим.

:::caution
Кореневі ключі, як-от `openai_base_url`, `model_provider` та `model_catalog_json`, **мають** стояти
перед заголовком першої `[table]`. Інтегратор гарантує це розміщення, вилучає власні застарілі/дублікатні
копії й ніколи не перезаписує кореневий `openai_base_url`, що належить користувачу; якщо такий існує,
синхронізація оновлює каталог, але повідомляє, що маршрутизацію не було впроваджено.
:::

## Спільний каталог моделей

Codex CLI, TUI, App і SDK читають той самий home Codex. opencodex розв'язує цю директорію з
`CODEX_HOME`, відкочуючись до `~/.codex`, і керує:

```text
$CODEX_HOME/config.toml
$CODEX_HOME/opencodex.config.toml
$CODEX_HOME/opencodex-catalog.json
$CODEX_HOME/models_cache.json
```

На WSL, якщо `CODEX_HOME` не задано, а Linux-файл `~/.codex/config.toml` відсутній, opencodex також
перевіряє наявність єдиного home Windows Codex Desktop за `/mnt/c/Users/*/.codex/config.toml`. Коли
існує рівно один кандидат, він використовує цю директорію, щоб режим app-server у WSL і Windows Codex
Desktop спільно використовували ті самі файли конфіга й автентифікації. Задайте `CODEX_HOME` явно, щоб
перекрити це виявлення.

У режимі окремого провайдера `requires_openai_auth = true` тримає інтерфейси Codex App/TUI, обмежені
акаунтом, узгодженими з нативним Codex. opencodex також обслуговує `/v1/responses` по WebSocket.
Окремий провайдер оголошує `supports_websockets = true` лише коли `"websockets": true`; на loopback
вбудований провайдер Codex може спершу спробувати WebSocket, і вимкнений проксі повертає `426`, тож
Codex відкочується на HTTP/SSE.

## Ідентичність тредів та історія

Типова loopback-форма зберігає нові треди позначеними нативним провайдером Codex `openai`, тож звичайна
історія відновлення не потребує перемапування. При першій синхронізації вона також мігрує треди,
позначені старішими збірками opencodex, назад до `openai`. Не-loopback режим окремого провайдера все
одно віддзеркалює історію під провайдером `opencodex`, поки активний, і відновлює резервні метадані при
виході. Задайте `syncResumeHistory: false`, щоб залишити історію недоторканою.

## Синхронізація каталогу моделей

Codex показує моделі з каталогу на диску (`$CODEX_HOME/opencodex-catalog.json` за замовчуванням). Під
час запуску та на `ocx sync` opencodex:

1. **Робить резервну копію** незайманого каталогу один раз у `~/.opencodex/catalog-backup.json` (щоб
   виведення було оборотним).
2. **Отримує** живі каталоги моделей прийнятних провайдерів (кешовано ~5 хв; відкочується до останнього
   доброго списку, потім до налаштованого `models[]`). Автентифікація forward не має ендпоінта моделей, а
   Cursor використовує свій RPC `GetUsableModels` замість `/models`.
3. **Зливає** маршрутизовані моделі як записи з простором імен (`provider/model`), клоновані з шаблону
   нативного каталогу Codex, щоб суворий парсер Codex їх прийняв.
4. **Фільтрує** `config.disabledModels` та непорожній allowlist `selectedModels` кожного провайдера.
5. **Переранжовує**, щоб виведені моделі сортувалися першими (див. нижче), потім записує злитий каталог
   назад.

Маршрутизовані записи каталогу також отримують переписану ідентичність GPT-5 на справжнє ім'я вихідної
моделі. Елементи керування міркуваннями походять із метаданих провайдера/моделі за драбиною Codex
`low | medium | high | xhigh | max | ultra`; непідтримувані значення відображаються або обмежуються
перед вихідним запитом.

### Власні відображувані назви моделей

Власна модель може нести зрозумілу людині **відображувану назву**, що перекриває мітку, яку Codex
показує в селекторі моделей, не змінюючи нічого в тому, як модель маршрутизується. Відображувана назва
відображається лише на поле `display_name` запису каталогу — маршрутизаційний slug (`<provider>/<model>`),
порядок колізій аліасів, провайдер і нативні маркетингові назви OpenAI залишаються недоторканими.

Додайте відображувану назву з CLI (проксі синхронізує каталог одразу, коли живий):

```bash
ocx models add deepseek deepseek-v4 --display-name "DeepSeek V4" --context-window 128000
```

Ви також можете задати чи відредагувати її через управлінський API (`POST /api/custom-models`,
`PUT /api/custom-models/<id>` з рядком `displayName`) та веб-панель. `/` відхиляється, бо він зіткнувся
б із розділювачем маршрутизаційного slug.

Відображувана назва **лише для показу й стабільна між регенераціями**. Кожен `ocx sync` та оновлення
каталогу заново виводять маршрутизовані записи з `config.json` (зокрема `customModels`), тож налаштована
назва застосовується повторно, а не дрейфує назад до маршрутизаційного slug. Керований перезапуск служби
також намагається зробити цю синхронізацію невдовзі після того, як проксі прив'яжеться. Якщо ця
best-effort завантажувальна синхронізація зазнає невдачі, наприклад під час офлайн-входу, зберігається
раніше збережений каталог, а наступний успішний `ocx sync` повторно застосовує налаштовану назву.
Справжні вихідні нативні назви (наприклад, `gpt-5.6-sol` → «GPT-5.6-Sol») походять із запінованого
вихідного знімка й ніколи не перекриваються власною відображуваною назвою.

### Зовнішні менеджери провайдерів

Якщо `config.toml` уже вибирає провайдера, відмінного від `openai` чи `opencodex`, OpenCodex залишає
файл без змін і пропускає записи профілю, оновлення каталогу/кешу та як негайну, так і фонову міграцію
історії Codex. Інструменти, що керують власним провайдером, часто позначають наявні сесії цим
ідентифікатором провайдера; заміна активного ідентифікатора може змусити ці цілі сесії зникнути з
перегляду історії Codex. Той самий захист застосовується до зовнішнього провайдера, вибраного застарілим
кореневим профілем.

Тримайте один інструмент власником конфігурації провайдера Codex. Щоб використовувати OpenCodex за
наявним менеджером провайдерів, вкажіть цьому провайдеру `http://127.0.0.1:10100/v1` з наскрізним
Responses (`wire_api = "responses"` у TOML Codex), а не трансляцією Chat Completions. Коли ввімкнено
автентифікацію API проксі, також передавайте `x-opencodex-api-key` з `OPENCODEX_API_AUTH_TOKEN`, як у
формі не-loopback провайдера вище. Щоб дозволити OpenCodex впроваджувати маршрутизацію напряму, спершу
поверніть Codex до його вбудованого провайдера `openai` та вилучіть будь-який кореневий `openai_base_url`,
що належить користувачу, потім знову запустіть `ocx start`.

### Усунення проблем із каталогом

Якщо модель відсутня в Codex або порядок/видимість каталогу виглядає неправильно, перевірте по порядку:

1. **`selectedModels`** на провайдері — непорожній allowlist показує Codex лише ці ідентифікатори;
   порожній чи опущений показує всі виявлені моделі. Ідентифікатор, якого немає в allowlist, ніколи не
   досягає каталогу.
2. **`disabledModels`** (верхній рівень) — приховує моделі і з каталогу, і з `/v1/models`, а також
   перемикає звичайні нативні GPT-slug-и на `visibility: "hide"`.
3. **`liveModels: false` з порожнім `models`** — коли живе виявлення вимкнено, а `models` порожній чи
   опущений, opencodex не показує маршрутизованих моделей для цього провайдера.
4. **Cursor `GetUsableModels`** — адаптер Cursor виявляє моделі через свій protobuf-RPC
   `GetUsableModels`, а не `/models`, тож зміна на боці Cursor може змінити, які ідентифікатори видимі,
   незалежно від інших провайдерів.
5. **Кеш та `ocx sync`** — живі каталоги кешуються приблизно на п'ять хвилин (`modelCacheTtlMs`, за
   замовчуванням `300000`). Запустіть `ocx sync`, щоб примусово отримати свіже й негайно переписати
   каталог.

:::caution[Інші локальні записувачі]
Записи каталогу (`opencodex-catalog.json`, `config.toml`) атомарні **всередині** opencodex, що лише
запобігає напівзаписаним файлам, коли два записувачі, що належать opencodex, змагаються. Це **не** зупиняє
інший локальний процес, файловий watcher чи агент синхронізації від перезапису видимості чи порядку
каталогу після того, як opencodex записав. Codex тримає свій окремий `models_cache.json` і може оновлювати
його незалежно, змінюючи видимий список без перезапису `opencodex-catalog.json`. Якщо моделі несподівано
перемикаються, поки проксі працює, зупиніть чи переналаштуйте конкуруючі записувачі, потім запустіть
`ocx sync` — це небезпека зовнішнього записувача, а не підтверджений дефект opencodex.
:::

## Селектор субагентів

`spawn_agent` у Codex оголошує перші **5 видимих у селекторі моделей каталогу** після сортування за
пріоритетом. `subagentModels` приймає до п'яти ідентифікаторів — або звичайні нативні GPT-slug-и, або
маршрути `provider/model` із простором імен — і дає їм пріоритети 0–4, щоб вони сортувалися першими:

```json
{
  "subagentModels": [
    "gpt-5.5",
    "gpt-5.6-sol",
    "anthropic/claude-opus-5",
    "xai/grok-4.5",
    "cursor/gpt-5.6-terra"
  ]
}
```

Ранжування за пріоритетом: виведені (0–4) < інші маршрутизовані (5) < нативні (9). Ви також можете
керувати цим із [веб-панелі](/opencodex/uk/guides/web-dashboard/).

## Розігрів акаунта Codex

Коли акаунт ChatGPT додається до пулу акаунтів Codex, opencodex перевіряє його перед збереженням
невеликим потоковим запитом до бекенда Codex Responses. Запит використовує справжній масив елементів
Responses (`input: [{ type: "message", ... }]`), чекає на `response.completed` і за замовчуванням
використовує `gpt-5.4-mini`. Якщо ця модель повертає HTTP 400, він повторює з `gpt-5.5`; структуровані
деталі вихідної помилки показуються без розкриття сирих тіл відповідей. Фонова ревалідація окрема й
вимкнена за замовчуванням; вона запускається лише коли ввімкнено Token Guardian, політика оновлення
`chatgpt` — `proactive`, а `tokenGuardian.codexWarmupEnabled` дорівнює true.

## Відновлення нативного Codex

opencodex ніколи вас не замикає. **`ocx stop` — це єдина команда, що повністю повертає до нативного
Codex** — вона зупиняє проксі, зупиняє фонову службу, якщо її встановлено, і прибирає кожен впроваджений
рядок та маршрутизований запис каталогу, тож звичайний `codex` працює точно так, ніби opencodex ніколи
там не було:

```bash
ocx stop       # зупинити проксі + службу, відновити нативний Codex
ocx restore    # відновити без зупинки  (аліас: ocx eject)
ocx restore back # знову вказати звичайний Codex на запущений проксі
```

Коли opencodex працює як керована [фонова служба](/opencodex/uk/reference/cli/#ocx-service), вона
встановлює `OCX_SERVICE=1`, тож перезапуск, керований службою, **не** тіпає конфіг Codex — лише явний
`ocx stop` / `ocx service stop` відновлює нативний Codex.
